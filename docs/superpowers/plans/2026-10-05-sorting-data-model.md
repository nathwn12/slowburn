# Sorting Data Model + Modified-Time Column Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Store each file's modification time, and replace the single-key sort with an ordered multi-key model where every key carries its own direction.

**Architecture:** Three layers, in order. (1) A new `modified` column on `tracks`, added by migration `06_*` following the exact idiom of `05_track_metadata.sql`, threaded through the scanner and the hand-written positional bind lists. (2) New `SortField` / `SortKey` Rust types exported to TypeScript by ts-rs, plus a **new additive** config field `library_sort_keys` — the existing `library_sort_by` / `library_sort_order` are left in place and untouched, because `Config` is deserialized from a file with `#[serde(default)]` and **changing a field's type would fail to deserialize an existing config file**, silently resetting a real user's settings. (3) A rewritten `sortTracks` that walks the keys in order, compares with `Intl.Collator`, and sorts missing values last under every direction.

**Tech Stack:** Rust (tauri v2 plugin, sqlx + SQLite, ts-rs), React/TypeScript, TanStack Query, Vitest.

**Spec:** `Q:\PROJECTS\PERSONAL\Slowburn\docs\specs\minimal-mode-and-sorting.md` §3.5, AC4–AC7. Recon: `Slowburn-ops\ui\recon\recon-sorting.md`, `recon-scanner-mtime.md`.

## Global Constraints

- Offline. No new network code.
- The app is **never launched** by this plan; verification is `cargo test` and `vitest` only. Tests stay muted.
- `src/generated/typings.ts` is generated by ts-rs — **never hand-edit it**.
- **Additive config only.** Do not remove or retype `library_sort_by` / `library_sort_order`. Old
  config files must still deserialize.
- **This plan does not touch `src-tauri/src/plugins/config.rs` until the UI-mode lane has committed**
  — that file is owned by another lane right now. Check `git log` for the `ui_mode` commit first.
- One writer per file. Nothing outside the file lists below.

## Review Focus

1. **A track with no such tag at all** versus one whose tag is the empty string. Both must sort last,
   and neither may throw. The spec says "missing tags sort last" and does not say what an empty
   string is — treat it as missing.
2. **The file is gone.** A row whose file was deleted has no mtime to read on rescan. It must keep
   its previous value rather than becoming null and jumping to the bottom of the library.
3. **Positional binds.** `database.rs` binds columns by hand in three places. A new column inserted
   in one list but not another produces a silent off-by-one that writes the wrong data into the
   wrong field. This is the single most likely way this change corrupts a library.
4. **Timestamps do not survive as text.** `modified` is stored as integer epoch millis, not an
   ISO string, precisely so string comparison cannot be used by accident — but the sort must
   therefore compare it numerically, and a `Collator` would sort it wrongly.
5. **An empty key list.** If `library_sort_keys` ever arrives empty (hand-edited config, failed
   migration), the list must still render deterministically rather than in whatever order SQLite
   returned.

- [ ] **Step 3: Implement `sortTracks`**

A stable multi-key comparison: for each key in order, resolve the field, compare with
`new Intl.Collator(undefined, { numeric: true, sensitivity: 'base' })` for text fields and
numerically for `Duration` / `DiskNo` / `TrackNo` / `PlayCount` / `DateAdded` / `FileModified`;
return on the first non-zero difference, applying that key's direction. Presence is decided before
value: a key where one side is missing and the other is not always yields "missing last", in either
direction. `DateAdded` is an ISO-8601 string and therefore compares as text; `FileModified` is a
number and must not. Never mutate the input; copy before sorting.

Then update the two call sites to pass `config.library_sort_keys`.

Then update `TrackListHeaderCell.tsx:54-63` so a header click writes **`library_sort_keys`** as a
single key (the clicked field, toggling direction when it is already the active field) rather than
`multiSet`-ing the legacy pair. This step is not optional polish: after this task nothing reads the
legacy fields, so without it every header sort button silently stops working. The badge,
asc→desc→off cycling and shift-click come later in Plan B; this step only keeps the buttons honest.

## Self-review

- **Spec coverage:** §3.5 model, per-key direction — Task 3. Default bundle — Task 2 step 1.
  Missing-last — Task 3. Comparison rules — Task 3 step 3. mtime storage — Task 1. AC4, AC6 — Task 3;
  AC7 — Task 3's non-mutation test.
- **Deliberately NOT in this plan:** the header badge / click-cycle / shift-click UI, the presets,
  the ignore-articles toggle's settings control, and the `mostPlayed` pagination fix. All of that is
  **Plan B**, which depends on Task 3's signature and cannot start before it lands.
- **Ignoring articles** is left out because it changes the comparator's *output* for every text
  comparison, and the spec fixes it as a toggle with no stated default. That is a decision to make
  with the spec's author, not to smuggle into a comparator.
- **Type consistency:** `SortField` → `SortKey.field` → `Track.modified` → `sortTracks(tracks, keys)`
  → `config.library_sort_keys`. One spelling each, no variants.
- **Known risk, resolved in the plan rather than left downstream:** deleting `getSortOrder` and
  `SORT_ORDERS` is safe — `SORT_ORDERS` is unexported, and recon found no call site for
  `getSortOrder`. The real break was the *write* side: `TrackListHeaderCell` persists the legacy
  pair, which nothing would read after Task 3, making the header buttons dead. Task 3 now rewrites
  that write path in the same task, so the UI never regresses between plans.
- **Legacy fields are left as dead weight on purpose.** `library_sort_by` / `library_sort_order`
  stay declared so an existing config file still deserializes. Removing them is a follow-up once a
  migration can rewrite old configs, and it is not worth risking a user's settings to tidy them.
